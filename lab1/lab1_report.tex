\section*{1. Kernel implementations}

\subsection*{Convolution}
The \texttt{convolution()} function computes a valid multi-channel 2-D convolution. It allocates an output for each filter, initializes each output element with its filter bias, and accumulates products over every input channel and kernel row and column. For input side length $N$ and kernel side length $K$, the output side length is $N-K+1$. The implementation uses nested loops over filters, output coordinates, channels, and kernel coordinates. Its arithmetic work is $O(F(N-K+1)^2CK^2)$, where $F$ is the number of filters and $C$ is the number of channels.

\textbf{Implementation details:} The output is stored as a three-level pointer structure indexed by filter, output row, and output column. Each output starts at its filter bias; the loops then accumulate the product of the corresponding input pixel and kernel coefficient across channels and kernel coordinates. The test driver initializes a 3-channel image and 2 filters. The implementation uses valid convolution with unit stride and no padding.

\subsection*{ReLU}
The scalar \texttt{relu()} function returns $x$ when $x>0$ and zero otherwise. \texttt{applyRelu()} applies this operation in place to every element of an input array, avoiding a second output allocation. This gives linear work in the input size.

\textbf{Implementation details:} The comparison returns the input unchanged when it is positive and zero for zero or negative values. The array helper applies this scalar operation in place. The functional test checks positive, zero, and negative examples.

\subsection*{Linear layer}
The \texttt{linear()} function implements a fully connected layer. It allocates one output value per output neuron, initializes that value with the corresponding bias, and computes the dot product between the input vector and that neuron's weight row. Its work is $O(I O)$ for input size $I$ and output size $O$.

\textbf{Implementation details:} Weights are addressed as \texttt{weights[outputIndex][inputIndex]}. The function allocates an output vector, initializes each output with its matching bias, then accumulates the input-weight products. The caller owns and frees the returned vector.

\subsection*{Matrix multiplication}
The \texttt{matmul()} function first checks that the left matrix column count equals the right matrix row count. It then allocates the result and uses the conventional three-loop algorithm: result row, result column, and inner product. Its work is $O(A_{rows}A_{cols}B_{cols})$ and it returns \texttt{NULL} for incompatible dimensions.

\textbf{Implementation details:} The function rejects incompatible dimensions when \texttt{A\_cols != B\_rows}. For compatible inputs, it allocates a row-pointer result matrix, initializes each \texttt{C[i][j]} to zero, and accumulates \texttt{A[i][k] * B[k][j]} over the shared dimension. The caller frees the result rows and outer pointer.

\subsection*{Softmax}
The \texttt{softmax()} function first finds the maximum input value, subtracts it before exponentiation for numerical stability, sums the exponentials, and returns the logarithm of each normalized probability. The returned values are log-probabilities, while exponentiating them gives probabilities whose sum is approximately one. The function allocates temporary exponential values and a separate output array.

\textbf{Implementation details:} Subtracting the maximum input before calling \texttt{exp()} reduces overflow risk without changing the normalized distribution. The implementation stores exponentials temporarily, sums them, writes \texttt{log(expValue / sum)} to a separate output vector, and frees the temporary array. The caller owns and frees the returned log-probability vector.

\section*{2. Tests implemented}
The Unity test driver in \texttt{tests/all\_tests.c} runs tests for convolution, neural-network helpers, functional operations, linear layers, and matrix operations. The tests check both ordinary cases and boundary or error cases: convolution behavior, flattening and prediction, softmax normalization, ReLU behavior, linear layers with zero/negative/large inputs and parameters, square matrix multiplication, and incompatible matrix dimensions.

The purpose of these tests is to verify numerical correctness independently of performance measurements. In particular, dimension checks and negative or zero values expose indexing, initialization, bias, and branch-handling errors that may not appear in one ordinary example.

\textbf{Additional test rationale:} The test driver runs the linear cases for zero weights and biases, negative weights and biases, and large-magnitude inputs, weights, and biases. Neural-network tests check channel-major flattening and prediction for a maximum, a tie, and mixed signs. Softmax is checked by verifying that exponentiated outputs sum to one and preserve the maximum index; matrix multiplication is checked for both a known product and incompatible dimensions. Some linear test functions are registered more than once in the driver, so the total invocation count includes repeats.

\subsection*{Convolution observations and bottleneck}
\textbf{Your interpretation:} The convolution implementation required a substantial amount of arithmetic work, which is reflected in the high retiring percentage. The main secondary limitation was execution-resource pressure, as indicated by the core-bound fraction, rather than delays due to memory fetches.

\subsection*{ReLU observations and bottleneck}
\textbf{Your interpretation:} The ReLU implementation involves a conditional branch for each element, which can lead to branch mispredictions depending on the input distribution. The relatively balanced profile indicates that memory access and simple arithmetic are not the primary bottlenecks, and the small size of the operation allows a significant portion of instructions to retire efficiently.

\subsection*{Linear observations and bottleneck}
\textbf{Your interpretation:} The linear layer's main bottleneck appears to be memory-bound, as indicated by the 16.4\% memory bound fraction. This suggests that the weight layout and cache behavior significantly impact performance, and optimizing the loop order to improve data locality could help reduce memory stalls.

\subsection*{Matrix multiplication observations and bottleneck}
\textbf{Your interpretation:} The matrix multiplication's high retiring fraction indicates that most of the computation is useful arithmetic work. The naive loop order may not fully exploit cache locality, but the predictable access patterns and regular computation allow the core to remain busy, minimizing frontend and speculation stalls. Optimizing the loop order for better cache reuse could further improve performance.

\subsection*{Softmax observations and bottleneck}
\textbf{Your interpretation:} The softmax implementation involves multiple passes over the input data, including computing the exponentials, summing them, and normalizing. This leads to temporary array usage and additional arithmetic operations. The profile resembles ReLU in terms of frontend and speculation fractions due to the conditional and loop overhead, but the backend bound is slightly higher because of the extra memory accesses and arithmetic involved in the multiple passes.

\section*{4. Debugging process}
I used the failing unit tests to isolate incorrect outputs, then ran the test binary under Valgrind with origin tracking. Valgrind reported an invalid read in \texttt{flatten()}; the code indexed the image as row-column-channel even though the allocated image is channel-row-column. Changing the access to \texttt{input[channel][row][column]} fixed the out-of-bounds read and stopped it from corrupting later tests. The softmax test also exposed that the function returned normalized probabilities while the implementation contract is log-softmax; returning the logarithm of each normalized exponential fixed the check that exponentiated outputs sum to one. After these corrections, the test driver reported 22 passing invocations and no failures. I also used profiler output to identify environment issues: perf counters were denied on the login node, and pinning with \texttt{taskset -c 0} failed when CPU 0 was outside the Slurm CPU set. Profiling succeeded after running on a compute node and removing the fixed CPU pin.

\section*{5. Performance improvements}
The top-down data suggests several optimization directions. Frontend-bound kernels could benefit from reducing instruction and branch overhead, improving loop simplicity, and enabling compiler optimization or vectorization. Backend-bound kernels could benefit from better data locality, contiguous allocations, improved loop order, blocking or tiling, and reducing unnecessary temporary allocations. ReLU may benefit from branchless or vectorized execution when appropriate; linear and convolution may benefit from contiguous layouts and SIMD-friendly inner loops; matrix multiplication is a candidate for cache blocking; and softmax could reduce passes and temporary storage while preserving numerical stability.

\textbf{Planned or measured improvements:} The frontend-bound kernels, such as ReLU and softmax, could benefit from reducing instruction and branch overhead through prefetching or vectorization. The backend-bound kernels, such as the linear layer and convolution, could benefit from improved data locality and vectorization to reduce memory stalls and repeated memory accesses.
